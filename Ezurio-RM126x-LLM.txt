# RM126x Live AT Interface Notes (Verified on Hardware)

This file records **observed behavior** from a real module on:

- Device: `/dev/ttyACM0`
- Date: **2026-02-16**
- Tools used: `minicom` and byte-level UART capture
- UART for host tests: `9600 8N1`, no flow control

## 1. Response Framing (Observed)

All module responses are framed as:

- Start: `0x0A` (`\n`)
- End: `0x0D` (`\r`)

Examples:

- `\nWAKE\r`
- `\nOK\r`
- `\nERROR 81\r`
- `\nJOIN: ...\r`

## 2. Wake/Sleep Behavior (Critical)

### Reliable wake sequence

1. Send `\r` (wake character)
2. Receive `WAKE`
3. Receive `OK`
4. Wait a short guard delay (~50 ms worked in testing)
5. Send real command

### Important observed behavior

If the module is sleeping and you send a command directly (example: `AT\r`), the command may be lost and you only get:

- `WAKE`
- `OK`

So host code should treat wake as a separate handshake step.

## 3. Command Results Verified Live

### Basic/info

- `AT` -> `OK`
- `ATI 0` -> `RM1261`, `OK`
- `ATI 3` -> `127.4.1.808`, `OK`
- `ATI 42` -> `2`, `OK` (application state: joined at test time)
- `ATI 3001` -> `1`, `OK` (connected at test time)
- `ATI 2000` -> `0`, `OK`
- `ATI 2001` -> `1`, `OK`
- `ATI 3007` -> `3`, `OK` (TX counter at test time)

### ATS/AT%S reads

- `ATS 302?` -> `115200`, `OK`
- `ATS 213?` -> `2000`, `OK`
- `ATS 213=?` -> `0..30000`, `OK`
- `ATS 629?` -> `2`, `OK`
- `AT%S 500?` -> `ERROR 89` (write-only)
- `AT%S 501?` -> returned DevEUI, `OK`
- `AT%S 502?` -> returned JoinEUI, `OK`

### Join/send/link/time/power

- `AT+DROP` -> `OK`
- `AT+SEND "0102"` when not joined -> `ERROR 81`
- `AT+JOIN` -> immediate `OK`, then async:
  - `JOIN: [OK], [TX]: ... [RX]: ...`
  - `ADRJ: ...`
- `AT+JOIN` followed immediately by a second `AT+JOIN` (while first join is in progress) -> second command returns `ERROR 14`
- `AT+SEND "01020304"` when joined -> immediate `OK`, async `TX: [ACK]...`
- `AT+TIME` -> immediate `OK`, async `TIME: [OK] YYYY:MM:DD:hh:mm:ss`
- `AT+LINKC` -> immediate `OK`, async `LC: [OK], M:<margin>, C:<gateway_count>`
- `AT+SUPI` -> immediate voltage reading (example `3307mV`), `OK`
- `AT+SUPS` -> `OK`; `SUP: <mV>` appears on next uplink (verified with subsequent `AT+SEND`)
- `AT+SLEEP` -> `OK`; next UART activity wakes module and returns `WAKE`, `OK`

## 4. Error Codes Confirmed in This Environment

- `ERROR 14` -> command rejected because current state is busy (reproduced by issuing `AT+JOIN` again before first join completed)
- `ERROR 15` -> unknown command (`AT+NOPE`)
- `ERROR 47` -> GPIO-related parameter issue observed on malformed `AT+DUTY` usage (`AT+DUTY` with missing arg)
- `ERROR 48` -> syntax/argument error (`ATI 3001?`)
- `ERROR 81` -> LoRa not joined when sending
- `ERROR 89` -> attempted read of write-only `%S` parameter

### `ERROR 14` Reproduction Trace (Observed)

Trigger sequence:

1. Wake (`\r`)
2. `AT+DROP`
3. `AT+JOIN`
4. Immediately send second `AT+JOIN` (about 30 ms later)

Observed response sequence:

- `WAKE`
- `OK` (wake empty command)
- `OK` (`AT+DROP`)
- `OK` (first `AT+JOIN` accepted)
- `ERROR 14` (second `AT+JOIN` rejected while join is in progress)
- later async: `JOIN: [OK] ...`
- later async: `ADRJ: ...`

## 5. Notable Firmware Behavior Differences vs Strict Spec Wording

The currently running firmware accepted both:

- `AT+SEND "ABC"`
- `AT+SEND 0102`

and produced successful `TX: [ACK]` asynchronous responses.

So in this firmware build, `AT+SEND` parsing is more permissive than “quoted, even-length hex only” wording would imply.

## 6. Host Integration Rules (Recommended)

1. Always do explicit wake handshake before functional commands.
2. Parse asynchronously at all times (JOIN/TX/RX/LC/TIME/SUP/ADRx can arrive later).
3. Keep reading long enough after `AT+SEND`/`AT+JOIN` to catch async completion lines.
4. Never treat immediate `OK` from `AT+JOIN`/`AT+SEND` as final success; final status is in async `JOIN:` / `TX:`.
5. If `ERROR 81` appears, force re-join workflow.
